# VigorSync 系统构建方案

## 1. 文档目的

本文定义产品第一版的系统边界、技术选型、进程划分、数据流、目录结构、部署方式和主要风险，作为后续编码与验收的统一基线。

## 2. 产品范围

### 2.1 第一版必须完成

- 深蹲、俯卧撑两种动作。
- 手机 App 发起、暂停、恢复和结束训练。
- 镜端显示摄像头画面、半透明骨架、当前动作、动作阶段、次数和明显错误提示。
- 本地 TTS 播报，不依赖云端。
- 训练视频、关键点、实时 rep 事件和错误提示本地保存。
- 训练结束自动提交离线分析，复用 RepChain 生成最终分段、评估、问题卡和报告。
- 手机查看训练历史、单次摘要和报告入口。
- 桌面浏览器查看详细回放报告。
- 单镜端、单用户、局域网部署。

### 2.2 第一版明确不做

- 多用户、云同步、排行榜和社交功能。
- 医学诊断、康复处方和伤病风险判断。
- 深蹲、俯卧撑之外的正式动作支持。
- 实时逐帧精细评分。
- 全自动机位和视角识别。
- 在镜端实时运行 RepChain。
- 直接使用 WorkoutTracker 的 TCN 结果替代最终离线分段。

## 3. 硬件与性能基线

| 项目 | 基线 | 说明 |
| --- | --- | --- |
| 显示屏 | 32 英寸 1080p | 横屏或竖屏均需全屏适配 |
| 摄像头 | USB 摄像头，支持 30/60 FPS | 采集可 60 FPS，推理不要求 60 FPS |
| 计算单元 | Raspberry Pi 5 8 GB 或同档迷你主机 | 优先保证推理与录像稳定 |
| 音频 | 本地音箱或 HDMI 音频 | TTS 本地播放 |
| 网络 | 家庭局域网 Wi-Fi | 手机与核心服务通信 |
| 存储 | 本地磁盘 | 训练视频可配置保留期 |

### 3.1 性能预算

- 镜端 UI：稳定 30 FPS 以上，画面切换不黑屏。
- 摄像头采集：目标 30 FPS；设备支持时可 60 FPS 采集并抽帧推理。
- 实时 Pose 推理：640x480 或 1280x720，目标 15–30 FPS。
- 实时状态：计数和阶段 5–10 Hz 更新即可。
- 镜端视频预览：640x480、15–20 FPS，优先本地回环，不经过外部网络。
- 启动到可训练状态：目标 5 秒内，模型首次加载不超过 10 秒。
- TTS：从触发到开始播报目标小于 1 秒。
- 单次上传上限沿用现有 `VLS/app` 的 512 MB。

## 4. 总体架构

```text
┌──────────────────────┐
│ Flutter 手机 App     │
│ 控制 / 摘要 / 历史   │
└──────────┬───────────┘
           │ REST + WebSocket（局域网）
           ▼
┌──────────────────────┐
│ Core API :8011       │
│ 会话、配对、任务编排 │
│ 历史、报告入口       │
└───────┬────────┬─────┘
        │        │
        │        └──────────────┐
        │                       ▼
        │              ┌──────────────────┐
        │              │ Offline Worker   │
        │              │ RepChain / 报告  │
        │              └──────────────────┘
        │
        │ 本机控制 / 状态
        ▼
┌──────────────────────┐        ┌──────────────────────┐
│ calimirror :8080     │◄───────┤ Live Engine :8020    │
│ 镜端 Kiosk UI        │ MJPEG  │ 摄像头 / Pose / 计数 │
└──────────────────────┘  WS    │ 录像 / TTS           │
                                └──────────────────────┘
```

所有高频视频和骨架数据留在镜端本机。手机只接收低频状态和最终报告，减少局域网带宽和隐私暴露。

## 5. 进程与职责

### 5.1 Core API

新增产品服务，复用 `VLS/app` 的后端与离线分析模块。

职责：

- 创建、查询和控制训练会话。
- 保存会话历史与手机配对信息。
- 向镜端和 Live Engine 下发命令。
- 接收 Live Engine 的低频状态并广播给 App。
- 在训练结束后创建离线分析任务。
- 对外提供报告和产物地址。

不负责：

- 摄像头采集。
- 实时 Pose 推理。
- 高频骨架广播。
- 镜端画面渲染。

### 5.2 Live Engine

新增 Python 服务，是第一版实时能力的核心。

职责：

- 独占摄像头设备。
- MediaPipe Pose 推理。
- 关节角度计算和动作状态机。
- Rep 计数、阶段判断、明显错误检测。
- 在画面上绘制骨架和调试信息。
- 提供本地 MJPEG 预览流。
- 提供实时状态 WebSocket。
- 本地 TTS 播报。
- 保存原始视频、关键点 JSONL、rep 事件和会话摘要。
- 停止后把产物路径交给 Core API。

第一版使用 MJPEG 而不是 WebRTC：

- 本地回环部署，延迟可接受。
- 前端实现简单，Electron 和普通浏览器均可显示。
- Python 端可以直接绘制骨架，镜端无需同步关键点坐标。
- 后续如果 CPU 或带宽压力明显，再升级 H.264/WebRTC。

### 5.3 镜端 UI

基于 `calimirror` 派生，保留 MagicMirror 的 Kiosk、待机模块和 Electron 能力。

职责：

- 待机显示时钟、天气和训练入口。
- 训练时切换为全屏训练布局。
- 显示 Live Engine 的 MJPEG 预览。
- 显示次数、阶段、置信度和告警。
- 显示加载、暂停、上传分析和报告就绪状态。
- 接收 Core API 命令并回报 UI 状态。

不负责：

- 打开摄像头。
- 运行 Pose 模型。
- 保存训练数据。
- 判断动作是否正确。

### 5.4 Flutter App

基于 `calimiro_app` 派生，作为手机伴侣端。

职责：

- 保存 Core API 地址和配对 token。
- 选择动作、视角和目标次数。
- 发起、暂停、恢复和结束训练。
- 查看实时 rep、阶段、置信度和错误提示。
- 查看训练历史和报告摘要。
- 提供报告链接或跳转。

第一版不要求 App 直接参与镜端推理。现有 ML Kit 和本地计数代码可作为离线演示和后续“手机传感器模式”，不进入主链路。

### 5.5 Offline Worker

复用 `VLS/app` 的 RepChain 运行模块。

职责：

- 读取训练视频和关键点。
- 重新提取或校验姿态。
- RepChain 分段与置信度计算。
- 分维度测量、评估和问题卡。
- 生成最终报告、证据帧和回放媒体。

离线结果是最终结果。实时计数只作为训练过程中的 provisional 信息。

### 5.6 WorkoutTracker

第一版不进入运行时关键路径。

候选用途：

- 离线动作类型分类。
- Rep 候选检测的第二意见。
- 训练集构建和模型实验。
- 后续替代人工选择动作类型的辅助能力。

不直接使用其 OpenCV 实时 Demo 作为镜端服务。

## 6. 源码复用策略

| 原项目 | 新产品位置 | 复用内容 | 不直接复用 |
| --- | --- | --- | --- |
| `VLS/calimirror` | `apps/mirror` | Kiosk、Electron、模块系统、待机页面思路 | 硬编码 8000 接口、现有训练业务逻辑 |
| `VLS/calimiro_app` | `apps/mobile` | Flutter UI、相机权限、页面结构 | 纯本地会话模型、无后端的历史逻辑 |
| `VLS/app` | `services/core-api`、`services/offline-worker`、`apps/report-web` | FastAPI、RepChain、问题卡、Vue 报告 | 单 worker 任务模型直接承担会话管理 |
| `VLS/WorkoutTracker` | 可选离线组件 | TCN 模型、数据集构建、训练代码 | 实时 Demo、产品主计数逻辑 |

原项目保留在 `VLS/` 作为参考，不通过 Git submodule 或软链接直接运行。产品代码选择性迁入新工作区，避免上游原型的不稳定接口影响产品。

## 7. 会话状态机

```text
created
  -> preparing
  -> active
  -> paused <-> active
  -> stopping
  -> analyzing
  -> completed

created|preparing|active|paused -> cancelled
created|preparing|active|paused|stopping|analyzing -> failed
```

完整迁移条件、触发方和终态约束见 `packages/contracts/session-state-machine.json`。Core 是状态写入方，Live Engine 只能通过内部事件请求迁移。

状态含义：

- `created`：Core 已创建会话，尚未启动设备。
- `preparing`：Live Engine 加载模型、打开摄像头。
- `active`：正在训练和实时计数。
- `paused`：摄像头可继续预览，但不累计 rep 和告警。
- `stopping`：停止采集并完成文件落盘。
- `analyzing`：离线分析任务排队或执行中。
- `completed`：报告可用。
- `failed`：启动、推理、落盘或分析失败。
- `cancelled`：用户取消或会话超时。

## 8. 端到端数据流

### 8.1 开始训练

1. App 调用 Core API 创建会话。
2. Core 创建 `session_id`，状态置为 `preparing`。
3. Core 调用 Live Engine 启动会话并通知镜端切换训练页面。
4. Live Engine 加载模型、打开摄像头并将状态置为 `active`。
5. 镜端打开本地 MJPEG 和实时状态 WebSocket。
6. App 通过 Core 的 WebSocket 接收低频状态。

### 8.2 训练中

1. Live Engine 以 15–30 FPS 推理，以 5–10 Hz 发布状态。
2. 镜端本机接收高频状态并即时更新画面。
3. Live Engine 每秒向 Core 上报一次摘要，Core 转发给 App。
4. 每次 rep 完成写入本地事件文件，同时发送 `rep.completed`。
5. 明显错误满足防抖规则后发送 `form.alert` 并触发 TTS。

### 8.3 结束训练

1. App 调用停止接口。
2. Core 通知 Live Engine 停止采集和镜像控制。
3. Live Engine 写入视频、关键点、事件和 `session_summary.json`。
4. Live Engine 调用 Core 的内部完成接口，提交本地路径和摘要。
5. Core 创建离线 job，并把 `session_id` 与 `job_id` 关联。
6. Offline Worker 生成最终报告。
7. App 和镜端显示报告已就绪。

## 9. 数据与存储

### 9.1 会话数据目录

```text
webdata/
└── sessions/
    └── <session_id>/
        ├── input/
        │   ├── source.mp4
        │   └── landmarks.jsonl
        ├── live/
        │   ├── events.jsonl
        │   └── summary.json
        └── complete.json
```

离线 job 继续使用现有 `webdata/jobs/<job_id>/` 结构，通过 `session_id` 关联。

### 9.2 核心表

- `sessions`：会话主记录和状态。
- `session_events`：rep、告警、暂停、恢复等低频事件。
- `jobs`：继续复用现有离线任务表。
- `pairing_tokens`：手机与镜端的局域网配对。

### 9.3 数据保留

- 原始视频默认本地保留 30 天，可配置。
- 派生报告默认长期保留，可单独删除原始视频。
- 支持按 session 一键删除视频、关键点和事件。
- 不在第一版上传视频到公网。

## 10. 安全与隐私

- Live Engine 只监听 `127.0.0.1`。
- 镜端 UI 只监听本机或受控局域网地址。
- Core API 对手机开放局域网端口，但必须使用配对 token。
- 所有写接口校验 token，并记录 session 所属设备。
- 训练视频默认加密存储或至少依赖系统磁盘加密。
- TTS、Pose 和评估默认全部本地运行。
- 日志不得输出视频内容、关键点明细或完整 token。

## 11. 部署方式

开发环境：

```text
core-api       127.0.0.1:8011
live-engine    127.0.0.1:8020
mirror         127.0.0.1:8080
```

生产环境使用 systemd 管理三个进程：

- `vigorsync-core.service`
- `vigorsync-live.service`
- `vigorsync-mirror.service`

启动顺序：

1. Core API。
2. Live Engine。
3. 镜端 UI。

相机设备、模型路径、存储根目录、端口和 token 密钥均通过环境变量或配置文件注入，不能硬编码。

## 12. 主要风险

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| Pi 5 上 Pose 推理不足 15 FPS | 计数延迟、漏 rep | 降低分辨率、抽帧、使用 Pose Lite、关闭非必要 UI 动画 |
| MJPEG 编码占用 CPU | 镜端卡顿 | 限制 640x480/15 FPS；必要时切换 H.264/WebRTC |
| 实时与离线计数不一致 | 用户困惑 | UI 标记实时结果为 provisional，报告以离线为准 |
| 两套 UI 维护成本高 | 开发变慢 | 严格区分镜端、手机端、桌面报告职责 |
| 摄像头被其他进程占用 | 会话启动失败 | Live Engine 独占设备并给出明确错误 |
| 代理或局域网不稳定 | 手机控制失败 | 镜端可本地降级启动；命令带超时和幂等 ID |
| 真实动作数据不足 | 误报或漏报 | 先支持两种动作，建立小规模自采回归集 |

## 13. 完成定义

第一版完成需要同时满足：

- 手机可以稳定开始和停止镜端训练。
- 镜端可以连续运行 10 分钟不崩溃、不黑屏。
- 深蹲和俯卧撑的实时计数可用且有防重复机制。
- 训练结束后能自动生成离线报告。
- 手机能查看本次训练摘要与历史记录。
- 报告中的问题卡可定位到视频时间点。
- 无云端依赖，默认数据留在本地。
