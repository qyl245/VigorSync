# VigorSync 实施路线与验收

## 1. 实施原则

- 先打通端到端闭环，再提高算法精度和界面完整度。
- 实时层和离线层分离，实时结果不作为最终评估结论。
- 每个阶段都必须有可演示、可回归的产物。
- 不在第一版引入多用户、云服务和复杂调度。
- 新产品工作区只迁入必要代码，不把四个原项目整体复制成单体工程。

## 2. 里程碑总览

| 阶段 | 目标 | 核心产物 |
| --- | --- | --- |
| M0 | 冻结方案与契约（已完成） | 文档、JSON Schema、OpenAPI、状态机、示例和校验器 |
| M1 | 镜端实时闭环 | 摄像头、Pose、骨架、计数、镜端 UI |
| M2 | 手机控制闭环 | 创建、启动、暂停、停止、状态同步 |
| M3 | 离线分析闭环 | 视频落盘、job 创建、报告生成、报告入口 |
| M4 | 产品化补强 | 历史、TTS、隐私删除、错误恢复 |
| M5 | 算法增强 | 小规模数据回归、WorkoutTracker 可选分类 |

### 4.3 验收

- 镜端连续运行 10 分钟不崩溃。
- 640x480 下 Pose 推理达到 15 FPS 以上。
- 深蹲、俯卧撑各 10 次测试中，实时计数误差不超过 1 次。
- 同一 rep 不重复计数。
- 摄像头断开或模型加载失败时有明确错误提示。
- 停止后视频和事件文件可正常打开。

### 4.4 M1 本机完成记录

2026-11-16 使用本机 USB 摄像头、640x480、30 FPS 和 MediaPipe Pose Lite CPU 推理完成：

- 最终版本连续运行 611.5 秒，始终为 `active`，没有崩溃或卡死。
- 采集 18,122 帧，推理 18,083 帧，因有界队列主动丢弃 38 帧；有效端到端采集约 29.6 FPS，单次推理耗时折算约 64 FPS。
- 工作集从约 298 MB 稳定到约 310 MB，私有内存在 964 MB 到 977 MB 之间，没有持续增长。
- 停止后生成了 91 MB 视频、42 MB 关键点和合法的事件/摘要文件；视频可在 OpenCV 中重新打开，首帧可读。
- 正视深蹲固定样本为 4/4 次；侧视俯卧撑固定样本为 17/18 次，相差 1 次。
- 2026-11-16 调整最短 rep 后的三组独立实测为 15/12/12 次，与人工记录完全一致。
- 右视俯卧撑两组独立实测为 9/8 次，与人工记录完全一致。
- 左视俯卧撑两组独立实测为 7/8 次，与人工记录完全一致；标准/差姿势回归样本为 19/18 与 14/14 次。
- 摄像头单帧链路在 20 帧冒烟中全部检测到 Pose，包含采集等待时约 16.6 FPS。
- MJPEG 首帧、WebSocket 指标、暂停/恢复、单摄像头互斥和停止落盘均已实测。
- Windows 摄像头默认使用 DirectShow，后续复测首帧从约 10 秒降至 2.5–3.2 秒。
- 录像时间轴从首帧开始计时，并对低于目标 FPS 的摄像头补帧，避免视频快放以及与事件时间错位。
- 推理线程默认限制为 20 FPS 并只处理最新帧；15.6 秒真实摄像头验证的有效吞吐为 19.33 FPS。
- JSONL 改为 64 KiB 缓冲并按秒刷新，减少逐帧磁盘 I/O；停止时强制刷新。
- MP4 写入移到独立异步线程，录像持续阻塞采集的情况已消除；15.5 秒复测保持 19 Hz 推理吞吐。
- MJPEG 与骨架合成限制为 15 FPS，相近测试运行时总 CPU 时间由约 16.7 秒降至约 15.0 秒。
- MediaPipe Tasks Pose Lite A/B 单帧耗时约 27.95 ms，对比当前 Solutions 的 28.70 ms 仅快 2.6%；但 180 帧样本仅检测到 104 帧姿态，准确性不达标，未替换主链路。
- 当前环境没有 FFmpeg，硬件 QSV 编码暂不接入；现有异步 `mp4v` 写入保留自动回退路径。
- 镜端训练页升级为动作遥测布局，新增暂停感知计时、目标进度、膝/肘主关节角仪表和 16:9/窄屏响应式排版。
- `live.metrics` 新增可选 `joint_angle`、`elapsed_s`；旧客户端可忽略，不破坏 v1 消息读取。
- 提供 `start_mirror.cmd`、`stop_mirror.cmd`、`status_mirror.cmd`，可一键管理实时引擎、页面服务和专用 Kiosk 浏览器。
- 提供 WebView2 轻量桌面外壳；窗口关闭会检查活动训练、确认停止并关闭内部服务。
- 已生成并实测约 8 MB 的 `VigorSyncLauncher.exe`，测试中窗口和两个端口均正常释放。
- `scripts/check_m1.ps1` 通过全部契约测试和 14 个 M1 单元/运行时测试。

本记录证明 M1 已在本机开发环境闭环。最终 Raspberry Pi 5 或迷你主机上的性能、

## 6. M3：离线分析闭环

### 6.0 M3 本机完成记录

2026-11-17 完成 M3 主链路：

- 新增 `services/offline-worker/`，锁定迁入 VLS 的 RepChain、配置、模型和报告运行时。
- Worker 仅监听 `127.0.0.1:8030`，数据写入 `webdata/offline/`，不直接暴露给手机。
- Core 在训练停止后自动创建 `job_*`，通过内部 token 提交本机视频路径。
- Core 轮询 Worker 的阶段和进度，通过 WebSocket 推送 `report.progress` 与
  `report.ready`，最终状态进入 `completed`。
- Worker 优先硬链接会话视频，失败时回退复制，避免重复大文件传输。
- 报告通过 Core 的高熵 `report_ticket` 地址访问，HTML 内的媒体和证据帧 URL
  自动重写，不需要把 pairing token 放入 URL。
- 手机历史页显示离线阶段和进度；完成后进入原生复盘页，展示离线/实时计数、
  质量状态、问题数和问题卡，并可打开完整 Web 证据报告。
- 镜端总结页跟随分析进度和完成状态；空闲配置页显示最近一次报告入口。
- 真实 20 秒俯卧撑视频完成完整离线流水线，生成 RepChain、问题、反馈 v2、
  媒体片段和 HTML 报告；Core 状态从 `analyzing` 正常进入 `completed`。
- 报告页采用 VigorSync 品牌视觉，支持桌面与手机响应式布局、Rep 分割时间轴、
  下降/上升相与底端标记、视频游标同步、问题证据定位和问题卡分层展示。
- 姿态质量门按已接受动作周期评估，排除录制开始准备和结束后走向设备停止的
  过渡帧；整段指标仍保留为诊断，动作周期内质量不足时继续 fail-closed。
- 该样本因拍摄时多人/出镜导致质量门拒答，系统正确返回 `quality_reject`，
  没有伪造动作纠正结论。
- M3 回归脚本 `scripts/check_m3.ps1` 覆盖 M2、Worker 导入和运行时文件检查。
- 当前测试：5 个 Flutter、8 个 Core、18 个 Live Engine、5 个契约和 5 个
  Offline Worker 测试通过；Android debug APK 和完整报告均可生成。

### 6.1 目标

训练停止后自动进入现有 RepChain 流水线，并能在手机和桌面查看报告。

### 6.2 任务

- 迁入 `VLS/app` 的 FastAPI、RepChain、配置、模型和 Vue 报告页。
- 增加 `session_id` 与 `job_id` 的关联。
- 增加内部完成接口，接收 Live Engine 的本地产物路径。

## 10. 第一版验收指标

### 10.1 功能

- 深蹲和俯卧撑均可完成完整训练闭环。
- 手机可以可靠控制镜端。
- 镜端可以看到实时计数和骨架。

- 手机可以查看历史与报告。

### 10.2 实时计数

- 标准测试集中，每 10 个 rep 的实时计数误差不超过 1 个。
- 同一 rep 不重复计数。
- 暂停期间不产生新 rep。
- 低置信度关键点不会触发 rep。

### 10.3 性能

- 镜端 UI 稳定 30 FPS 以上。
- Pose 推理 15 FPS 以上。
- 10 分钟训练不崩溃、不内存泄漏。
- 预览流在本地回环下延迟低于 500 ms。
- 停止训练后 5 秒内进入离线分析。

### 10.4 数据与安全

- 无公网依赖。
- Live Engine 仅监听本机。
- 手机请求必须通过 token。
- 训练视频可一键删除。
- 日志不输出 token 和视频内容。

## 12. 进入编码前必须确认的决策

- 目标硬件最终是 Raspberry Pi 5 还是迷你主机。
- 摄像头型号、分辨率、FPS 和安装高度。
- 镜端横屏还是竖屏。
- 是否需要训练视频默认录制，还是用户可选。
- 手机 App 是否只做同一局域网控制，还是需要后续远程访问。
- 第一版是否必须支持中文 TTS，以及是否接受本地合成音色。

这些决策不会改变总体架构，但会影响硬件采购、性能预算和验收基线。
